# 云笺（Cloudleaf）翻译接口与提供者规范

- 文档路径：`docs/translation-api.md`
- 文档版本：2.0，2026-10-22
- 适用范围：本地词典释义、短语翻译、整句翻译、离线模型、用户自定义 API、缓存、隐私和错误处理

## 1. 设计目标

翻译系统为云笺提供统一、可替换的翻译能力，但不得成为基础输入的运行前提。

系统需要区分两类任务：

1. **候选释义查询**：短文本、本地优先、低延迟，结果用于候选注释。
2. **整句翻译**：用户明确发起，允许耗时更长，使用异步任务，并返回完整译文。

两类任务可以共享语言标识、提供者管理和缓存基础设施，但不能使用相同的延迟策略和 UI 行为。

## 2. 功能范围

完整产品按T1本地双向词语/短语、T2整句工作流、T3离线模型与自定义API建设，详见[路线图](roadmap.md)及[产品范围](product-scope.md)。词性、多义、词形、搭配、大索引/缓存/版本与独立查询均纳入T1，原型annotation并未实现这些能力。项目不提供公共在线翻译服务器、默认账号或开发者自己的API Key。

模型选型需实际比较中英双向、口语/书面/长句、数字/单位/专名/标点保留、CPU延迟、峰值内存、体积/首次加载、Windows离线部署及代码/权重许可；本接口文档不代表任何后端已交付。基础输入始终不等待翻译。

翻译方向：

- 中文 → 英文。
- 英文 → 中文。
- 自动识别源语言（作为辅助能力，必要时允许用户手动指定）。

基础输入不依赖自动语言识别成功与否。

## 3. 核心术语

- **Provider（提供者）**：一种具体翻译来源，例如本地词典、离线模型或自定义 API。
- **Request（请求）**：具有唯一 ID、输入文本、源语言和目标语言的翻译任务。
- **Task（任务）**：请求从排队、执行到完成或取消的生命周期。
- **Annotation（候选注释）**：候选词旁的简短释义，不是可直接提交的译文。
- **Sentence Translation（整句翻译）**：对用户选定文本生成完整译文的显式任务。
- **Provider Policy（提供者策略）**：依据用户偏好、可用性和任务类型选择提供者的规则。

## 4. 统一类型

接口以 Rust 为核心实现。以下类型是概念基线，实际实现可以根据异步运行时、错误处理和版本兼容性调整。

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum Language {
    Auto,
    Chinese,
    English,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum TranslationKind {
    Gloss,
    Phrase,
    Sentence,
}

#[derive(Debug, Clone)]
pub struct TranslationRequest {
    pub request_id: u64,
    pub kind: TranslationKind,
    pub text: String,
    pub source: Language,
    pub target: Language,
    pub input_revision: Option<u64>,
}

#[derive(Debug, Clone)]
pub struct TranslationResponse {
    pub request_id: u64,
    pub translated_text: String,
    pub source: Language,
    pub target: Language,
    pub provider_id: String,
    pub from_cache: bool,
}
```

实际实现还需定义统一错误类型、耗时信息、任务取消状态、模型版本和必要的诊断字段。不得把 API Key、认证头或不必要的完整请求文本放入日志字段。

## 5. 提供者接口

所有提供者必须实现统一的能力声明与调用约定。可以使用 async trait、装箱 Future 或由任务调度器包装同步本地查询；具体方案在依赖冻结时确定。

接口至少需要表达：

- 提供者唯一 ID。
- 支持的语言方向。
- 支持的任务类型。
- 可用状态和初始化错误。
- 执行翻译任务。
- 取消任务或忽略过期任务的能力。
- 关闭与释放资源的行为。

建议的逻辑接口：

```text
TranslationProvider
  id() -> ProviderId
  capabilities() -> ProviderCapabilities
  health() -> ProviderHealth
  translate(request, cancellation) -> Result<Response, TranslationError>
  shutdown() -> Result<(), TranslationError>
```

本地词典可实现低开销查询接口；离线模型和网络 API 必须由异步调度器调用。不得在输入法按键回调内同步等待 `translate`。

## 6. 提供者类型

### 6.1 LocalDictionaryProvider

用途：单词、短语、候选释义。

要求：

- 默认优先使用。
- 查询索引常驻内存或采用经基准测试确认的低延迟方案。
- 返回短释义、词性和必要的来源标识。
- 不在每次按键时扫描完整词典文件。
- 不将来源不明的网页抓取结果直接打包。
- 查询未命中时返回明确的未命中状态，不阻塞候选生成。

词典查询未命中不代表输入候选不存在。候选生成与翻译注释必须保持独立。

### 6.2 OfflineModelProvider

用途：中译英、英译中整句翻译。

要求：

- 通过统一提供者接口接入。
- 支持模型路径、版本、语言方向和加载状态查询。
- 模型加载在后台进行。
- 支持任务取消或结果过期过滤。
- 能够报告模型缺失、加载失败、资源不足和推理失败。
- 不可用时不影响基础输入。
- 在随包分发模型前，必须独立核实模型权重、词表、运行库和相关数据的许可证。

第一版不要求自研或训练神经机器翻译模型。先完成适配接口，再选择经过评估的模型。

### 6.3 CustomApiProvider

用途：连接用户自己配置的在线服务。

配置项建议包括：

- 服务显示名称。
- API 地址。
- 接口类型或协议适配器。
- 模型名称（如服务要求）。
- 凭据引用，不直接暴露明文密钥。
- 请求超时。
- 允许的语言方向。
- 是否允许整句文本发送。
- 是否允许结果缓存。
- 连接测试状态。

不得假定所有在线服务都完全兼容同一种请求与响应格式。应通过明确的协议适配器实现不同服务，而不是在核心中散布特例。

## 7. 提供者选择策略

策略应由用户设置控制，并且每次选择结果可诊断。

建议默认规则：

1. 候选释义先查询本地词典和本地缓存。
2. 整句翻译按用户指定的默认提供者执行。
3. 用户选择离线优先时，先检查离线模型是否可用；若不可用，根据设置提示或回退。
4. 用户选择在线服务时，只有在明确授权文本发送的前提下才发起请求。
5. 远端失败后，只能按照用户允许的回退规则尝试其他提供者。
6. 不得悄悄把原本指定为本地处理的文本发送到远端。
7. 若无可用提供者，返回明确错误，不影响输入法继续运行。

## 8. 异步任务与过期结果

每个任务必须拥有唯一请求 ID。与当前输入候选相关的请求还应关联输入修订版本或候选 ID。

当输入内容发生变化时：

- 可以取消不再需要的后台任务。
- 即使底层任务无法立即取消，也必须忽略过期结果。
- 旧结果不得覆盖新输入的候选注释。
- 整句翻译面板关闭后，不应自动把迟到的结果上屏。
- 用户再次发起翻译时，旧任务不能污染新任务的状态。

任务状态建议包括：`Queued`、`Running`、`Succeeded`、`Failed`、`Cancelled`、`Expired`。

## 9. 超时、重试与限流

网络请求必须设置连接超时和总请求超时。具体数值应在用户设置和基准测试中确定，并提供合理默认值。

重试规则：

- 只对明确可重试的错误重试。
- 遵守服务端限流响应。
- 避免用户连续输入时产生请求风暴。
- 不自动无限重试。
- 用户取消后不再重试。
- 输入法退出时应停止或安全收尾后台请求。

候选注释不应在每次字符输入时发起在线请求。首期候选注释使用本地词典；在线 API 主要用于用户明确发起的整句翻译。

## 10. 缓存策略

缓存需要区分词典结果缓存和整句翻译缓存。

### 词典缓存

- 以词条 ID、语言方向和词典版本为主要键。
- 词典升级后使相关缓存失效。
- 允许用户关闭缓存或重置索引。

### 整句翻译缓存

缓存键至少考虑：

- 规范化输入文本的安全摘要。
- 源语言和目标语言。
- 提供者 ID。
- 模型或服务版本（可获得时）。
- 影响译文的配置参数。

整句文本可能包含敏感信息，因此缓存应默认采用谨慎策略。可以默认不持久化整句翻译结果，仅保留短期内存缓存；若提供持久化选项，必须让用户明确开启并能够清除。

缓存中不得保存 API Key 或认证头。

## 11. API 安全与隐私

### 11.1 用户知情

在用户配置在线服务前，界面应说明：输入文本会发送给用户填写的服务端点，具体数据处理方式取决于该服务的条款和隐私政策。

在线服务默认关闭。不能因为在线服务配置了 API Key，就默认上传所有候选文本或完整输入上下文。

### 11.2 凭据存储

优先使用操作系统凭据存储：

- Windows Credential Manager 或等效安全设施。
- macOS Keychain。
- Linux Secret Service 或其他经用户确认的安全设施。

如果目标环境没有可用凭据设施，应明确提示风险，并采用最小暴露的替代方案。不得把真实密钥写入仓库、测试夹具、崩溃报告或普通日志。

### 11.3 网络目标

- 外部服务优先使用 HTTPS。
- 验证 TLS 证书。
- 对重定向设置限制。
- 设置请求体和响应体大小上限。
- 不执行服务端返回的任意代码。
- 对本地或局域网地址的使用应由用户主动配置，不得从不可信内容中自动推导请求地址。
- 连接测试只发送明确的测试请求，不上传当前编辑器中的文本。

### 11.4 日志

日志记录请求 ID、提供者 ID、耗时、错误类别和缓存命中状态即可。默认不记录完整原文、译文、API Key、认证头或完整请求 URL 中可能包含的敏感查询参数。

## 12. 统一错误类型

至少区分：

- `UnsupportedLanguagePair`
- `UnsupportedTaskKind`
- `ProviderUnavailable`
- `ModelNotFound`
- `ModelLoadFailed`
- `AuthenticationFailed`
- `RateLimited`
- `NetworkUnavailable`
- `Timeout`
- `InvalidResponse`
- `ResponseTooLarge`
- `Cancelled`
- `Expired`
- `InternalError`

错误码面向程序稳定；用户界面负责将其转换为可理解的本地化提示。错误信息不得直接展示密钥或不可信服务返回的任意内容。

## 13. 翻译质量评估

翻译质量不能只凭少量手工示例判断。测试集应覆盖：

- 日常对话。
- 商务邮件和报价语句。
- 语序不同的中英文句子。
- 否定、时态、数量、日期和单位。
- 专有名词、缩写和产品名称。
- 标点、换行和较长句子。
- 中英混合输入。
- 模糊或上下文不足的表达。

数据必须有合法来源或由项目独立编写。记录模型版本、方向、测试集版本和评估方法，不能把一次主观检查作为发布质量保证。

## 14. 验收标准

- [ ] 本地词典查询不依赖网络。
- [ ] 候选注释不进入提交文本。
- [ ] 整句翻译采用异步任务。
- [ ] 任务具有唯一 ID，并能处理取消和过期结果。
- [ ] 在线 API 默认关闭。
- [ ] 用户明确授权后才发送文本到在线服务。
- [ ] API Key 不进入源代码和普通日志。
- [ ] 网络超时、模型失败不会阻止基础输入。
- [ ] 缓存可按提供者、语言方向和版本失效。
- [ ] 每个随包模型均有独立许可证记录。
- [ ] 连接测试不会上传用户当前输入。
