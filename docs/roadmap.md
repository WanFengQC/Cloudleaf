# 云笺（Cloudleaf）开发路线图

- 文档路径：`docs/roadmap.md`
- 文档版本：1.0
- 当前阶段：M1 工程初始化与 M2 平台无关输入核心原型已完成本地验收
- 首发目标：Windows 上可正常输入、候选选择、显示本地双语释义的可安装 MVP

## 1. 路线图原则

1. 先建立可独立测试的 Rust 核心，再接入 Windows 系统输入法。
2. 先保证基础输入稳定，再增加翻译能力。
3. 词典与整句翻译均纳入总体规划，但分阶段交付。
4. 在线翻译和重型离线模型始终与实时输入路径隔离。
5. 不以“编译通过”作为里程碑完成的唯一条件。
6. 每个阶段都有明确交付物、测试要求和退出条件。
7. macOS/Linux 从第一天保持架构预留，但不要求在 Windows MVP 前同步交付完整适配。

## 2. 阶段总览

| 阶段 | 目标 | 主要交付 |
|---|---|---|
| M0 | 冻结文档和技术决策 | 五份开发文档、决策记录、许可证政策 |
| M1 | 工程初始化 | Rust workspace、CI、基础类型和错误规范 |
| M2 | 自研输入核心原型 | 输入状态机、全拼解析、候选生成与排序 |
| M3 | Windows 输入法 MVP | TSF 接入、候选窗口、文本提交 |
| M4 | 本地双语词典 | 数据导入、词典索引、候选释义 |
| M5 | 整句翻译基础流程 | 统一 API、翻译面板、任务取消与结果上屏 |
| M6 | 离线模型和用户 API | 可插拔提供者、凭据管理、故障回退 |
| M7 | 稳定性与发布 | 性能优化、安装升级、发布材料 |
| M8 | macOS / Linux 扩展 | 平台适配、跨平台回归和打包 |

阶段不绑定固定日期。只有前置验收通过后才进入下一阶段。

## 3. M0：文档与技术基线

### 任务

- M0-01：确认产品名称为“云笺”，英文品牌名为“Cloudleaf”。
- M0-02：维护 `architecture.md`。
- M0-03：维护 `input-behavior.md`。
- M0-04：维护 `translation-api.md`。
- M0-05：维护 `testing.md`。
- M0-06：维护 `roadmap.md`。
- M0-07：制定第三方代码、词典、模型与素材的许可证审查规则。
- M0-08：确定第一阶段 Windows 测试环境。

### 交付物

- 五份文档可以独立维护。
- 核心与平台层的边界明确。
- 首期范围、性能目标与测试标准明确。
- 第三方来源登记模板可用。

### 退出条件

所有首期开发任务都有明确输入、输出、测试和验收条件；不存在必须依赖某个在线服务才能运行基础输入的设计。

## 4. M1：工程初始化

### 任务

- M1-01：建立独立 Git 仓库。
- M1-02：锁定稳定版 Rust 工具链与 MSRV。
- M1-03：建立 Cargo workspace。
- M1-04：创建最小公共类型 crate。
- M1-05：定义统一错误类型与日志策略。
- M1-06：配置格式检查、静态检查和测试。
- M1-07：建立 Windows CI；尽可能加入公共核心的 Linux 构建。
- M1-08：建立依赖与许可证清单。

### 交付物

- 可重复构建的空工程。
- 自动化测试能在 CI 中运行。
- 依赖版本和工具链明确。
- 仓库不含真实密钥或未经授权的数据。

### 退出条件

新环境可以按照文档完成构建与测试；核心 crate 不依赖 Windows 专属 API。

## 5. M2：自研输入核心原型

### 任务

- M2-01：实现平台无关输入事件。
- M2-02：实现输入状态机。
- M2-03：实现全拼解析器。
- M2-04：定义最小词典数据格式。
- M2-05：实现本地词典查询原型。
- M2-06：实现候选生成。
- M2-07：实现可重复的候选排序。
- M2-08：建立输入固定语料。
- M2-09：建立核心性能基准。

### 交付物

- 可通过命令行测试程序或测试宿主验证输入流程的 Rust 核心。
- 拼音、候选和状态转换单元测试。
- 候选排序回归报告。
- 初步延迟与内存数据。

### 退出条件

核心能够对固定输入序列产生预期候选；退格、取消、提交和异常输入有测试；核心处理路径不执行网络请求。

## 6. M3：Windows 输入法 MVP

### 任务

- M3-01：验证 TSF 最小接入原型。
- M3-02：评估 Rust COM 绑定；必要时确定薄 C++ 桥接方案。
- M3-03：实现输入法注册、激活和停用。
- M3-04：将系统按键转换为统一核心事件。
- M3-05：实现组合文本更新和最终提交。
- M3-06：实现候选窗口和数字选词。
- M3-07：处理焦点变化、取消与生命周期。
- M3-08：在真实 Windows 应用中进行集成测试。

### 交付物

- 可安装、可启用的 Windows 输入法原型。
- 能完成基础中文拼音输入和候选提交。
- 系统集成问题和兼容性测试记录。

### 退出条件

在记事本、浏览器文本框和多行编辑器中通过基础输入测试；不会因一次 Enter、Space 或候选提交产生重复文本；基础输入不依赖翻译服务。

## 7. M4：本地双语词典

### 任务

- M4-01：选定可合法分发的词典数据源。
- M4-02：实现 Python 词典导入、清洗与校验工具。
- M4-03：定义词条、释义、词性和来源数据格式。
- M4-04：实现高频查询索引。
- M4-05：接入候选释义。
- M4-06：处理多义词和长释义显示。
- M4-07：完善数据许可证与版本清单。

### 交付物

- 本地中英词典与短语数据。
- 可重复生成的词典数据管线。
- 候选旁释义显示。
- 词典质量和许可证报告。

### 退出条件

词典不可用或查询未命中时，基础输入仍正常；释义不进入提交文本；词典查询性能达到项目测试目标。

## 8. M5：整句翻译基础流程

### 任务

- M5-01：定义统一翻译请求、响应和错误类型。
- M5-02：实现提供者管理接口。
- M5-03：实现异步任务生命周期。
- M5-04：实现独立整句翻译面板。
- M5-05：实现源语言和目标语言选择。
- M5-06：实现复制译文和明确确认后的直接上屏。
- M5-07：实现取消、过期结果过滤和基础缓存。
- M5-08：建立中英双向翻译测试集。

### 交付物

- 可通过测试提供者演示的整句翻译流程。
- 统一翻译 API 文档与测试。
- 任务取消和过期结果测试。

### 退出条件

翻译流程与输入状态机分离；用户关闭面板或继续输入时，迟到的结果不会自动上屏或覆盖新内容。

## 9. M6：离线模型与用户自定义 API

### 任务

- M6-01：评估候选离线翻译模型和运行方式。
- M6-02：核实模型、词表和运行库许可证。
- M6-03：实现离线模型适配器。
- M6-04：实现用户自定义 API 协议适配器。
- M6-05：实现凭据安全存储。
- M6-06：实现超时、错误分类、限流和用户可控回退。
- M6-07：实现模型状态和服务连接测试。
- M6-08：验证在线服务默认关闭和隐私说明。

### 交付物

- 至少一种经过质量和许可证审查的离线模型适配方案，或明确的未完成原因。
- 用户自定义服务配置流程。
- 密钥存储与日志隐私测试。
- 翻译提供者故障隔离报告。

### 退出条件

没有在线服务时基础输入仍正常；API Key 不进入仓库和普通日志；用户明确授权后才发送文本；离线模型失败不会导致输入法崩溃。

## 12. 任务优先级

### P0：首期阻塞项

- Rust workspace 和可重复构建。
- 输入状态机与全拼解析。
- 候选生成、排序和提交。
- Windows TSF 原型。
- 本地词典查询。
- 基础性能与回归测试。

### P1：首发必要能力

- 候选释义。
- 设置中心。
- 用户词频与用户词典基础能力。
- 整句翻译面板与统一 API。
- 隐私、日志和安装流程。

### P2：扩展能力

- 离线翻译模型。
- 自定义在线 API。
- 更多拼音方案。
- macOS 与 Linux 适配。
- 高级上下文排序和可选翻译缓存。

优先级不代表可以跳过架构设计。P2 功能可以延后实现，但其接口边界应在需要时明确，不能提前堆入未验证的复杂度。

## 13. 每个任务的标准模板

每个开发任务必须记录：

- 编号和标题。
- 所属阶段与模块。
- 目标及非目标。
- 前置任务。
- 输入与输出。
- 实现范围。
- 依赖与许可证影响。
- 隐私与安全影响。
- 自动化测试。
- 性能影响。
- 验收标准。
- 完成记录与相关提交。

跨模块接口、数据格式或用户可见行为发生变化时，必须先更新相应文档，再合并实现。

## 14. 发布前总检查

- [ ] 基础输入完全不依赖网络服务。
- [ ] Rust 核心与平台适配边界清晰。
- [ ] 核心算法由项目独立实现。
- [ ] 输入固定语料回归通过。
- [ ] 性能指标有真实测量结果。
- [ ] Windows 真实应用测试通过。
- [ ] 词典、模型、依赖和素材授权可追溯。
- [ ] 在线服务默认关闭。
- [ ] 密钥不进入源代码、日志和测试样例。
- [ ] 翻译失败不会导致基础输入失效。
- [ ] 安装、升级、卸载和配置迁移已测试。
- [ ] 版本号、变更记录和发布文件一致。

## 15. 变更管理

路线图是可演进的计划，不是对发布日期的承诺。调整阶段顺序时，应记录原因、风险和验收影响。

任何架构变更都必须评估：

- 是否影响核心平台无关性。
- 是否把耗时工作带入实时输入路径。
- 是否改变用户可见输入行为。
- 是否引入新的第三方许可证或数据风险。
- 是否需要补充性能和兼容性测试。

只有通过评审的变更才能成为新的开发基线。
