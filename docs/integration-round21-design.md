# Round 21 输入与离线翻译整合设计

从输入分支的 `714f8c9439148b23d2ce34dc3a4e672d59598c1d` 建立 `codex/integration-round21`。翻译模块从 PR #5 的 `cca77457ca3943ee5ad90d566a8d9ef6b8795cd2` 按路径引入。保留两条功能线的 workspace 成员、依赖审计、许可、测试与 CI。复用固定翻译依赖作解析起点，以 Cargo 1.90.0 重新解析合并后的成员。

输入核心提供明确确认译文的入口。入口检查当前输入修订、活动状态、未决提交和译文边界，通过现有提交事务分配编号。翻译提交不产生 SelectionEvidence。候选和原文回退继续走既有入口。此变更不会在常规按键路径创建翻译服务、读取权重或调用提供者。

独立的 `cloudleaf-bridge` 持有同一会话的 InputEngine，使用翻译服务的有界后台 worker。在显式翻译动作捕获当前候选或用户提供的英文、会话、修订、词典、方案和模型版本。状态就绪后再次核对绑定，用户明确确认才创建输入提交。翻译任务和输入提交各自保留身份。Applied 完成，NotApplied 等待显式重试并取得新提交编号，Unknown 保留恢复信息并等待宿主核对后开启新会话。

桥接默认只接受离线提供者。模型文件以固定清单校验，模型准备和推理在后台或无窗口准备阶段进行。取消和过期通过现有任务令牌与会话绑定处理。HEAD、授权模型身份与耗时证据分别记录。现有翻译面板和在线凭据实现保留，窗口人工验收保持暂停。

先通过无窗口双向事务回归和真实本地权重推理，再进行固定搜索集和逐键对照。原资源预算、窗口暂停、研究模型分发与正式语言质量门禁继续适用。
